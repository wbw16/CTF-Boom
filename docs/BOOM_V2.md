# Boom V2 变更设计

> 历史设计记录。solver-slimming 分支已删除 V2 baseline/checkpoint/branch/verifier/recovery
> 实现；本文不再描述当前产品接口。

状态：M1–M5、受控执行环境、输出治理与评估工具已实现（2026-08-01）

桌面补充：模型仍只在设置中选择一次；设置内提供 OpenCode Provider、凭据和可编辑模型管理器。
设置还提供具名“破甲提示词”库。每个 Provider 模型可通过下拉菜单选择一条；实际调用该模型
时，Boom 将提示词置于 Agent 系统提示词最前面，并统一覆盖主求解、检查点、会诊与 subagent。
删除提示词会清除所有引用，不影响模型调用。
历史运行继续保留在磁盘和 API 中，但不再以“不同模型工作区”的横向标签条呈现。

## 0. 实现落地摘要

本设计已经在 CLI 和桌面 runner 中落地。M1/M2 原实现和 `finish=length` 最多一次恢复保持
不变；本轮从有界基础采集开始，按 M2.5 → M3 → M4 → M5 → 输出治理/评估的顺序完成。

实际模块映射：

| 能力 | 实现 |
|---|---|
| Intake 与 baseline 时机 | `src/baseline.ts` |
| Python 档案、Conda 发现、任务绑定 | `src/environment.ts` |
| argv-only 受控执行与三种模式 | `src/command-executor.ts`、`resources/plugin/boom-exec.ts` |
| 模式 B 证据分支 | `src/branches.ts` |
| trigger、信息增益、阶段和动作门控 | `src/orchestrator.ts` |
| 模式 D 确定性优先/盲化验证 | `src/verifier.ts` |
| 历史效果聚合 | `src/evaluation.ts`、`boom evaluate` |

运行流程现为：新任务先固化环境绑定并完成一次有界 intake，再创建 `baseline-complete`
检查点；裁决给出多个可区分实验时建立独立证据分支。solver 请求隔离执行、依赖安装或其他
高成本动作时，运行时先返回宿主门控信号；宿主执行 falsification 检查点和强模型反证分支，
批准后才创建续跑会话。solver 结束后宿主对产物与机器状态做 reconciliation，检测新增表面、
假设冲突、根假设否定、阶段变化和低信息增益。候选由宿主按远程适配器、本地 checker、
离线推导、盲化模型的顺序验证。

实现边界：CTF 远程服务没有统一提交协议，因此远程确定性验证以 `DeterministicVerifier`
适配器接入；没有适配器不会伪造 remote 验证级别。容器缺失时 `isolated` 明确失败，绝不
静默降级。Provider 模型目录的超大 output 数值只作为目录元数据，Boom 在运行时将单回合
输出限制为 32K tokens，并叠加宿主字符上限、流式退化检测和 compaction 恢复记录。

适用范围：Boom 的 API 模型编排、任务状态、subagent 调度、验证流程和桌面交互

不包含：模型训练、参数合并、LoRA 合并、MoE、供应商内部推理算法

## 1. 背景

Boom V1 已经具备持久任务、模型切换、会诊、subagent、预算控制、运行事件和候选 Flag
审核能力。当前多模型能力采用固定流程：

1. 两个不同模型读取同一份有限快照，并行生成计划；
2. 第三个不同模型综合两份计划；
3. 求解模型执行综合计划；
4. 只有首次规划、手工请求或 `stalled`、`budget`、`error` 等停止状态才会触发会诊。

这个流程能够证明多模型 API 调用、并发、持久化和预算扣减是可行的，但它存在以下产品
问题：

- 多模型产生的是多份文字计划，而不是相互独立的证据；
- 固定要求模型不同，可能为了表面多样性引入能力较弱的模型；
- 会诊专家不能实际检查文件或运行实验，容易输出通用建议；
- 手工会诊依赖 `NOTES.md`，当任务记忆不完整时上下文不足；
- 关键阶段没有检查点，只能依赖人工判断或等待任务停滞；
- 没有区分探索、执行、反证和验证，所有问题都使用同一种“生成并综合”模式；
- subagent 没有明确的经济模型/强模型分配政策；
- 最终候选的独立验证仍弱于求解本身。

Boom V2 将多模型能力从“固定会诊功能”改成“由任务状态驱动的检查点和分支系统”。

## 2. 产品目标

Boom V2 的目标是：

1. 默认由单个合适模型持续推进，不为简单任务支付固定的多模型成本；
2. 在完成基础采集、取得阶段突破、出现证据冲突或即将做出高成本决策时主动进入检查点；
3. 把多模型的差异用于独立假设、实际取证、反证和验证，而不是重复撰写计划；
4. 让便宜模型承担边界清楚、能够自动验收的工作；
5. 让强模型集中处理开放推理、跨证据综合、关键路线选择和无确定性验证器的判断；
6. 所有模型调用、证据、分支、预算和裁决均可追踪、可取消、可恢复；
7. 保持已确定的 Boom 安全边界：已知正确 Flag 不进入运行工作区，任务产物留在
   `work/`，运行时依赖继续封装在 `src/runtime.ts`。

## 3. 非目标

Boom V2 不做以下事情：

- 不合并不同供应商模型的权重；
- 不训练模型路由器；
- 不假定任一供应商模型具有可靠的自报置信度；
- 不把每个阶段边界都机械地转换为三模型会诊；
- 不让多个 agent 无边界地在同一目录中互相覆盖产物；
- 不使用“讨论轮数”或“运行时间”作为唯一的重新分析依据；
- 不把 LLM 判断当作本地 checker、远程服务或可复现推导的替代品。

## 4. 核心设计原则

### 4.1 CTF 是证据驱动的循环

Boom V2 把求解过程描述为：

> 采集 → 决策检查点 → 分支实验 → 状态更新 → 必要时重新决策 → 阶段突破 →
> 独立验证

阶段只是用户可理解的进度表达；真正触发多模型调用的是任务信息状态发生重要变化。

### 4.2 先保证质量，再追求差异

模型不再被强制要求全部不同。一个检查点可以采用：

- 同一强模型的两个独立上下文；
- 两个经过实测、能力接近但特长不同的模型；
- 一个强分析模型和一个经济型反对者；
- 单一强模型加若干实际执行的经济型 worker。

选择依据是任务、角色、历史效果和预算，而不是供应商名称是否不同。

### 4.3 事实、假设和决定分离

模型输出必须区分：

- **事实**：由文件、工具输出、远程响应或可复现实验支持；
- **假设**：对事实的解释，尚待验证；
- **实验**：能够支持或否定假设的下一步动作；
- **决定**：当前选择哪条路线及为什么；
- **候选**：可能的 Flag、密钥、明文或利用链；
- **验证**：候选是否通过独立检查。

自由文本可以作为人类阅读视图，但不能是唯一的机器状态。

### 4.4 工具优先于模型判断

当结果能够由确定性工具验收时，不调用额外模型作最终判断。模型负责提出和解释，工具负责
能自动判定的事实。

## 5. Boom V2 求解阶段

### 5.1 Intake：输入采集

目标：形成完整、受限、可重复使用的任务快照。

采集内容：

- 题目说明和 Flag 格式；
- 附件清单、大小、哈希、真实文件类型；
- 外层归档和已展开文件清单；
- 远程目标和协议提示；
- 已有 `NOTES.md`；
- 当前任务、历史 turn、停止原因和用户否定的候选；
- 已生成的重要产物及其路径；
- 最近新增的事实和已排除方向。

这一阶段优先使用宿主程序、确定性工具和经济型 agent。只有出现格式矛盾、异常载荷或需要
跨文件判断时才升级到强模型。

### 5.2 Baseline：攻击面建立

基础快照完成后自动进入第一次决策检查点。该检查点不能只做摘要，必须产出：

- 攻击面或解题面分类；
- 相互区分的主要假设；
- 每个假设的证据需求；
- 按信息价值和成本排序的实验；
- 每个实验的停止条件；
- 推荐的 worker 档次和预算；
- 下一次检查点触发条件。

### 5.3 Recon：循环侦查

Boom 按裁决结果执行一个或多个受限分支。分支必须围绕具体假设实际运行工具、读取材料并
保存证据。

只要当前路线持续获得符合预期的新证据，而且下一步清楚、便宜、可撤销，就继续执行，不
重新调用完整多模型检查点。

### 5.4 Breakthrough：阶段突破

当取得改变问题结构的中间结果时，例如恢复出新文件、识别出协议、定位到校验函数、获得
密钥材料或确认漏洞原语，任务进入新的检查点。

检查点重新评估剩余假设，但保留已经确认的证据和关闭的方向，不从题面重新开始。

### 5.5 Exploit / Derive：利用或推导

这一阶段由强模型负责跨证据推理和核心路径。经济型 worker 继续承担：

- 可自动测试的脚本实现；
- 明确参数的批处理；
- 协议重放；
- 结果比较；
- 已知变体枚举；
- 产物整理。

在高成本操作、不可逆动作或关键前提仍不确定时，先触发反证审查。

### 5.6 Verify：独立验证

出现候选结果后，不允许原求解模型仅凭自我确认结束任务。验证顺序为：

1. 本地 checker；
2. 远程服务；
3. 文件格式、哈希、解码或推导脚本的确定性复现；
4. 独立模型盲化复现或反证；
5. 用户审核。

验证失败会形成新的事实，进入下一次检查点，而不是丢弃原工作区或重新开始。

## 6. 四种多模型模式

### 6.1 模式 A：探索型会诊

用途：

- 首次基础快照完成；
- 新阶段开始；
- 原核心假设被否定；
- 多个方向都有真实证据。

默认流程：

1. **分析者**提出最可能的解释和实验；
2. **挑战者**独立寻找替代解释、遗漏和反例；
3. **裁决者**读取两者及原始证据，生成有序分支。

要求：

- 分析者和挑战者使用独立会话；
- 不要求模型名称不同；
- 裁决者必须直接看到原始任务快照，不能只看到两份计划；
- 输出采用结构化假设和实验，不直接宣布猜测成立；
- 普通检查点可以使用强分析者、经济型挑战者和强裁决者；
- 高歧义、高风险检查点使用两个强分析者和独立强裁决者。

### 6.2 模式 B：证据分支

用途：

- 两个以上方向值得用实验区分；
- 单个方向会产生大量工具输出；
- 不同方向可以安全并行；
- 需要避免主模型上下文被原始输出淹没。

每个分支包含：

- 唯一目标；
- 关联假设；
- 已知输入；
- 允许使用的工具和路径；
- 模型档次；
- token 和时间预算；
- 成功、失败和停止条件；
- 必须产生的证据文件和报告。

分支工作目录：

```text
work/branches/<branch-id>/
  branch.json
  report.json
  REPORT.md
  artifacts/
```

worker 不直接修改其他分支或任务级状态。分支结束后由宿主合并其报告，主控制器决定是否把
某个产物提升为任务级关键产物。

### 6.3 模式 C：反证审查

用途：

- 一条路线明显领先，但仍依赖未经验证的前提；
- 即将投入高成本操作；
- 结果符合预期得过于顺利；
- 模型输出与工具结果之间存在细微矛盾；
- 候选只有格式匹配或模型自报验证。

反证者不继续原路线，而是尝试：

- 找出未验证前提；
- 构造能够推翻结论的实验；
- 检查偏移、截断、编码、字节序和伪阳性；
- 检查产物是否来自当前输入；
- 检查脚本是否把候选硬编码或从不可信来源带入结果；
- 给出最便宜的反证动作。

反证审查默认使用强模型。已有确定性工具能够完成反证时不调用模型。

### 6.4 模式 D：独立验证

用途：

- 出现 Flag、密钥、明文、利用链或最终解释；
- 用户否定过相同或相近候选；
- 原模型无法提供可复现路径；
- 验证来源只有模型自述。

要求：

- 优先执行确定性验证；
- 模型验证者不得看到候选的模型来源和自报置信度；
- 能够盲化复现时，从原始事实和关键产物重新推导；
- 不能盲化时，验证者以否定候选为目标；
- 模型意见只能产生 `model-review`，不能冒充 `local-checker`、`remote` 或
  `offline-derivation`；
- 正确 Flag 仍由宿主保存，不写入 agent 工作区。

## 7. 检查点触发策略

### 7.1 自动触发

满足任一条件时创建检查点：

1. `baseline-complete`：基础任务快照首次完成；
2. `new-surface`：出现新的文件类型、协议、服务行为、算法或可执行路径；
3. `hypothesis-conflict`：两个有证据支持的假设互相冲突；
4. `root-assumption-rejected`：当前路线的核心前提被否定；
5. `phase-transition`：取得足以进入下一破解阶段的关键产物；
6. `high-cost-action`：下一步预计消耗显著时间、token 或远程尝试；
7. `risky-action`：下一步涉及执行不可信程序或复杂远程交互；
8. `candidate-found`：出现最终候选；
9. `candidate-verification-failed`：候选未通过独立验证，需要反证原推导并更换求解视角；
10. `low-information-gain`：连续若干相互独立实验没有产生新事实、关闭假设或推进阶段；
11. `manual`：用户主动要求检查。

`low-information-gain` 使用显式事件判断，不依赖模型自报置信度。一次实验只有在以下至少
一项发生时才算取得进展：

- 新增可引用事实；
- 支持或否定一个现有假设；
- 发现新的有效分支；
- 关闭一个方向；
- 产生新的关键产物；
- 进入下一阶段；
- 改善候选的验证级别。

默认在连续三项独立实验均无上述变化时触发检查点。该阈值必须可配置。

### 7.1.1 无人值守恢复

恢复控制由宿主按结构化原因触发，而不是由失败模型自行决定：

- 精确工具/文本循环：新建 turn，并轮换到另一个已配置模型一次；
- 空回复或畸形输出：同模型干净重试一次，仍失败再轮换一次；
- `low-information-gain`、`root-assumption-rejected`、`hypothesis-conflict`：运行多模型检查点和证据分支，再由新 solver 继续；
- 候选独立验证失败：运行反证检查点，保存失败验证并更换 solver；
- 相同恢复原因只自动处理一次（输出异常最多“重试 + 轮换”两次），恢复链共享原任务剩余预算并设熔断。

权限、路径、工具缺失、执行环境、远程不可达和 Provider 临时故障不属于认知恢复；它们由确定性修复、退避或 Provider fallback 处理，不能通过多模型会诊扩大重试。

### 7.2 不触发

以下情况不创建完整检查点：

- 新结果符合当前路线，下一步明确且低成本；
- 只需继续运行已经验证的脚本；
- 只需整理输出或更新持久状态；
- 确定性验证器已经给出明确结果；
- 只有一个方向有证据，其他方向只是无依据猜测；
- 同一个模型只是希望重新措辞或补充原计划。

## 8. 模型档次和 subagent 政策

Boom V2 使用能力档次而不是硬编码供应商：

```text
economy   边界清楚、可自动验收、低成本
strong    开放推理、跨证据综合、关键裁决
```

用户可以为每个档次选择具体的 `provider/model`。Boom 保存选择，但不根据名称猜测能力。

### 8.1 经济型模型任务

适合经济型模型的任务：

- 文件清单、类型、大小、哈希和元数据整理；
- 对长日志、strings 或反编译结果作有路径引用的分块提取；
- 按固定规则比较输出；
- 已明确算法且有测试的脚本实现；
- 已知编码、压缩或参数变体枚举；
- 重放确定的协议流程；
- worker 报告去重和分类；
- 检查要求的产物是否存在；
- 监控长任务和报告异常；
- 维护结构化状态的人类可读视图。

经济型任务必须有明确输入、输出、成功条件和预算。不能把“分析一下整个题目”交给经济型
模型。

### 8.2 强模型任务

必须优先使用强模型的任务：

- 首次判断混杂材料中的关键现象；
- 从不完整证据建立和排序假设；
- 跨文件、代码、协议和运行结果综合；
- 逆向语义恢复；
- 密码攻击条件判断；
- 漏洞链和复杂利用路径设计；
- 冲突证据裁决；
- 核心假设崩溃后的重新规划；
- 无确定性验证器时的反证和独立验证；
- 判断是否值得投入大量预算。

### 8.3 升级规则

一个经济型 worker 执行后，出现以下任一情况就升级，不连续调用多个经济模型盲目重试：

- 未按结构化格式交付；
- 混淆事实和猜测；
- 结论与引用证据矛盾；
- 实际任务范围超出分支定义；
- 需要同时理解多个产物；
- 已经执行成功但无法解释结果；
- 下一步选择会显著影响总成本或安全。

如果失败原因是工具缺失、文件路径、限流或临时 API 错误，应先修复运行问题，不升级推理
模型。

### 8.5 受控执行环境

模型档次解决 API 成本问题，不解决命令执行边界。Boom V1 的 `bash` 直接运行在宿主环境，
继承宿主 `PATH`，Python 虚拟环境也由模型临时决定是否创建。提示词中的“不要修改系统”只能
约束正常行为，不能提供可复现性或安全隔离。

Boom V2 把执行环境作为模式 B 证据分支之前必须完成的基础层，目标分为三部分：

1. **可复现**：同一任务的后续 turn 使用同一受管环境，并记录解释器和依赖；
2. **控制宿主改动**：默认禁止修改共享环境；只有用户显式授权时才允许安装，并完整记录；
3. **安全隔离**：执行不可信程序时不能访问宿主用户目录、凭据或其他任务。

#### 8.5.1 禁用内置 bash 直通

求解 agent 和 worker 不再直接获得运行时内置的无限制 `bash`。Boom 提供自己的受控命令
工具，所有命令都经过宿主执行器：

- 固定工作目录为当前任务或当前分支；
- 使用白名单构造子进程环境，不继承完整 `process.env`；
- 不向命令进程暴露 Provider API key、Boom 凭据和桌面进程环境；
- 统一执行超时、输出上限、取消、事件记录和退出状态；
- 拒绝修改工作区外路径和调用系统包管理器；
- 记录实际解释器、命令、工作目录和环境配置版本。

仅修改 `PATH` 或增加 shell alias 不能构成约束，因为绝对路径可以绕过。真正的命令边界必须
位于 Boom 自己的工具和执行器中。

#### 8.5.2 Python 环境

Boom 把 Python 解释器及其依赖视为一个具名的“环境配置档案”（environment profile）。网安
用户通常长期维护一套包含 pwntools、angr、z3、pycryptodome 等工具的 Conda 环境；它应当
被多个题目直接复用，而不是每题创建或克隆一套 Python 环境。

环境选择分为两级：

1. **GUI 全局默认**：设置页必须选择一个默认环境配置档案，之后创建的任务直接使用它；
2. **单题覆盖**：新建任务时可以继承默认值或选择其他环境，任务详情中也可以显式切换。

创建任务时，Boom 将当时的配置档案 ID、规范化路径和环境指纹固化到任务状态。之后修改 GUI
全局默认值不会改变正在运行或已有的任务。解析顺序固定为：

```text
单题环境 > GUI 默认环境
```

没有可用的默认环境时，GUI 引导用户完成选择，CLI/批量运行则在开始前明确失败。Boom 不自动
创建题目级 venv，也不静默回退到系统 Python。

每次创建 solver 或 worker 会话时，Boom 必须在 system prompt 中动态加入一条不可由用户提示
覆盖的环境声明：

```text
本题选择的 Python 环境是“{displayName}”（{kind}，Python {version}，安装策略：{installPolicy}，执行模式：{executionMode}，指纹：{fingerprint}）；python/pip 已由 Boom 路由到该环境，禁止自行激活、切换或修改其他 Python 环境。
```

这条声明由任务固化的环境绑定生成，不从模型输入或当前 shell 猜测。主 agent 与所有 worker
看到相同声明；切换单题环境后，新会话使用新声明，已有会话必须结束后重建。路径等调试细节
保留在 `environment.json` 和 GUI，不必放入 prompt。检查点 agent 不执行命令，但其任务快照
应包含同一份环境摘要，以便判断建议的实验当前是否可执行。

支持的 Python 配置档案：

| 类型 | 行为 | 适用场景 |
|---|---|---|
| `conda` | 直接调用已有 Conda 环境的解释器 | 推荐；用户长期维护的通用网安环境 |
| `python` | 直接调用用户明确选择的 Python 解释器 | 不使用 Conda 的已有工具环境 |

设置页通过 `conda info --json` / `conda env list --json` 发现 Conda 环境，也允许用户手动选择
Conda prefix 或 Python 可执行文件。运行时直接使用规范化后的解释器路径，不依赖
`conda activate` 或用户 shell 初始化脚本。选择环境时必须探测 Python 版本、架构、关键包和
可执行性，并给出“测试环境”结果。

每个配置档案定义依赖策略，默认为 `deny`，即 agent 可以使用已安装工具，但不能自行执行
`pip install` 或 `conda install`。用户可以在 GUI 中显式改为 `allow`；此时安装会修改这套共享
环境，必须显示确认其影响范围并记录安装事件。安装不可信包或执行未知程序仍应使用
`isolated`，不能依赖 Python 环境提供安全边界。

每个任务只保存对共享环境配置档案的绑定、指纹和题目私有运行数据，不复制解释器和依赖：

```text
work/.boom/environment.json
work/.boom/cache/pip/
work/.boom/tmp/
work/.boom/home/
```

通用规则：

- `python`、`python3`、`pip` 和 `pip3` 始终解析到任务绑定的解释器和环境；
- 按探测结果设置 `CONDA_PREFIX` 或 `VIRTUAL_ENV`，不为普通解释器伪造激活状态，并构造
  受控 `PATH`；
- 设置 `PYTHONNOUSERSITE=1`，清除宿主 `PYTHONPATH`；
- 禁止 `--user` 和系统级安装，并执行配置档案的依赖策略；
- `HOME`、`TMPDIR`、`XDG_CACHE_HOME`、`PIP_CACHE_DIR` 和常见工具缓存指向
  `work/.boom/`；
- 允许安装时必须经过 Boom 环境工具，记录请求包、解析版本、来源、时间和结果；
- 后续 turn 复用同一环境，不因切换模型重新创建；
- 所有任务和证据分支默认复用所选配置档案，不为 subagent 创建 Python 副本；
- `environment.json` 记录配置档案来源、规范化解释器路径、Python 版本、平台、关键包、
  工具版本、环境指纹和执行模式；
- 题目私有缓存不作为解题证据，历史文件浏览默认折叠或隐藏其大体积内容。

切换单题环境属于显式状态变更：先停止该任务正在执行的命令，创建环境切换检查点，重新探测
能力并记录事件。已有分析产物不删除，但之后的结果必须带新环境指纹。环境不可用时任务进入
可恢复错误状态，不能静默换用系统 Python 或其他 Conda 环境。

共享 Conda/Python 环境解决的是工具链一致性，不是安全沙箱。Python 包安装脚本和被分析
程序仍然可能访问宿主，因此执行隔离继续由受控命令工具和容器负责。

#### 8.5.3 执行模式

Python 环境选择与进程隔离是两个正交维度：前者决定常用工具链，后者决定某条命令能访问
什么。Boom 提供三个明确执行模式，禁止静默降级：

| 模式 | 行为 | 适用范围 |
|---|---|---|
| `managed` | 受控命令工具、清洁进程环境、所选共享 Python 环境；仍使用宿主内核 | 模型生成的分析脚本、常规文件处理 |
| `isolated` | 在一次性容器中执行，`challenge/` 只读、`work/` 可写、无宿主凭据 | 不可信二进制、安装第三方包、动态利用 |
| `static-only` | 禁止执行挑战程序和第三方安装，只允许读取和静态工具 | 无可用隔离环境时的安全回退 |

常规分析默认使用 `managed`，从而复用用户选定的 Conda/Python 工具链。执行未知二进制、
不可信安装脚本或其他高风险命令时，单次命令必须提升到 `isolated`；容器使用其预置工具链，
不克隆题目的 Python 环境。未安装受支持的容器运行时，则该类命令进入 `static-only` 或向用户
报告，不能自动在宿主执行。

隔离模式至少满足：

- 容器内非 root 用户；
- 只挂载当前任务；
- `challenge/` 只读，`work/` 可写；
- `/tmp` 和用户目录使用任务私有目录或 tmpfs；
- 设置 CPU、内存、进程数、磁盘和墙钟限制；
- 默认无网络；需要远程题目时只开放题目声明的目标；
- 包下载由宿主环境工具单独代理和审计，不把通用网络权限交给求解命令；
- 容器销毁后，只有 `work/` 中的产物和环境清单保留。

#### 8.5.4 非 Python 工具

相同边界适用于 Node、Ruby、Java、编译器和系统工具：

- 禁止 `brew`、`apt`、全局 `npm`、系统 `gem` 等宿主安装；
- 项目级依赖只能写入 `work/.boom/` 或分支环境；
- 优先提供预装、版本固定的 CTF 工具镜像；
- 每次运行记录实际工具版本；
- agent 需要缺失工具时提交环境请求，而不是自行修改宿主。

#### 8.5.5 桌面和 doctor

设置页增加执行环境状态：

- 当前默认模式；
- 默认 Python 环境配置档案；
- 自动发现的 Conda 环境及其 Python 版本、位置和健康状态；
- 新建任务的环境下拉框，以及任务详情中的环境覆盖和切换入口；
- 当前任务环境的来源、指纹和安装策略；
- 容器运行时是否可用；
- 是否允许包安装和远程网络；
- 当前共享环境信息和任务私有缓存大小；
- 重新探测环境操作。

`boom doctor` 检查受控命令工具、所选 Python 解释器、容器运行时和凭据隔离。环境不满足任务
要求时应在开始前失败，不能运行到中途才发现解释器或隔离层不可用。

## 10. API 调用和编排

### 10.1 快照

每种角色接收按职责裁剪的 `TaskSnapshot`，而不是完整模型对话或未经筛选的工具日志。

快照必须包含：

- 当前阶段和检查点原因；
- 题目基本信息；
- 相关事实及证据路径；
- 当前假设及状态；
- 已排除方向；
- 活跃或刚完成的分支；
- 候选和验证状态；
- 可用预算；
- 该角色的唯一任务。

裁决者必须看到原始快照和候选报告。不能只根据其他模型的摘要作决定。

### 10.2 并发

- 模式 A 的分析者和挑战者可以并发；
- 模式 B 的独立分支可以并发；
- 裁决必须等待必需的输入完成；
- 单个分支失败不应自动取消其他分支；
- 用户取消、任务总预算耗尽或检查点超时会取消全部相关调用；
- 免费或已知不支持并发的供应商必须串行或禁用并发。

### 10.3 预算

预算分为：

- 任务总预算；
- turn 预算；
- 检查点预算；
- 分支预算；
- 单次调用预算。

每次模型调用继续记录 raw tokens、billable tokens、费用和墙钟时间。检查点必须在调用前
验证剩余预算，不允许完成会诊后才发现没有执行预算。

默认策略：

- 普通任务最多同时运行两个分支；
- 明确有三个相互独立方向时允许三个；
- 普通检查点最多两个分析输入和一个裁决调用；
- 验证调用不与求解调用共享预算上限，但仍计入任务总消耗；
- 达到预算时优先保存状态和证据，不生成冗长总结。

- `python` 和 `pip` 不能落到用户未选择的系统环境；
- GUI 可以选择默认 Conda 环境，新建任务默认继承该选择；
- 单题可以覆盖默认环境，且不会改变其他任务或全局默认值；
- 修改全局默认环境不会影响已有任务；
- Conda 环境不可用时明确报错，不能静默切换解释器；
- 未配置默认环境时不能启动任务；
- 默认依赖策略下 Boom 不会自动安装、升级或删除共享环境中的包；
- solver 和 worker 的 system prompt 准确声明当前题目绑定的环境、安装策略和执行模式；
- 切换单题环境后旧会话停止，新会话中的环境声明和实际命令解释器一致；
- 模型无法通过受控命令读取 Provider API key 或宿主用户目录；
- 多个任务可以复用同一 Python 环境，但临时目录和工具缓存保持题目级分离；
- 同一任务切换模型后继续复用原环境；
- 未提供隔离环境时不能执行未知二进制；
- 取消和预算超限能够终止命令及其子进程；
- 旧任务首次继续时要求选择或确认环境，不需要迁移已有产物。

### M3：模式 B 证据分支

- 建立隔离分支目录；
- 为 worker 增加分支合同；
- 支持 economy / strong worker；
- 合并结构化报告；
- 实现并发、取消和分支预算。

验收：

- 两个分支不能覆盖彼此文件；
- 一个分支失败不影响另一个完成；
- 报告中的证据路径必须存在且位于分支目录；
- 分支进展能更新无进展计数；
- 用户取消能终止全部子调用。

### M4：自动触发和阶段循环

- 实现其余检查点触发；
- 实现阶段转换；
- 实现连续无信息增益阈值；
- 自动决定继续执行还是重新检查；
- 桌面展示阶段、分支和触发原因。

验收：

- 不需要等到 timeout 或 stalled 才能主动检查；
- 正常推进不会频繁重复会诊；
- 新关键产物能够触发阶段检查点；
- 高成本操作可以在执行前暂停并请求裁决。

### M5：模式 C/D 和验证

- 实现反证角色；
- 实现确定性验证优先级；
- 实现盲化模型验证；
- 记录验证来源和级别；
- 接入现有正确/错误候选审核循环。

验收：

- 原求解模型不能单独把候选标记为已验证；
- 本地 checker 存在时不浪费模型验证调用；
- 模型验证不会升级成工具验证级别；
- 用户否定候选后保留证据并重新进入检查点；
- 正确 Flag 只保存于宿主状态。

## 15. 已确定的产品决策

以下决策在 V2 实施期间视为默认，不重复讨论：

1. 只考虑 API 调用层的模型组合；
2. 多模型不是默认常驻，而是检查点能力；
3. 第一次完整基础采集后必须有检查点；
4. 阶段突破、证据冲突、高成本动作和候选出现会主动检查；
5. 多轮无进展通过信息事件判断，不等待整个任务超时；
6. 模式 A/B/C/D 分别承担探索、取证、反证和验证；
7. subagent 按任务可验收程度选择 economy 或 strong；
8. 不强制不同角色使用不同模型；
9. 确定性验证优先于模型验证；
10. `NOTES.md` 继续作为紧凑人类可读记忆，机器编排状态单独持久化；
11. V1 任务和会诊记录保持可读；
12. 正确 Flag 永远不进入求解工作区。
13. solver 和 worker 不直接使用继承宿主环境的内置 `bash`；
14. 所有任务默认复用 GUI 选定的 Conda/Python 环境，不按题创建 Python 环境；
15. Python 环境只提供共享工具链，不被描述为安全沙箱；
16. 执行未知二进制必须使用隔离模式，缺失隔离能力时禁止静默回退；
17. Provider 凭据和完整宿主环境永远不进入求解命令进程。
18. Python 环境按“单题覆盖、GUI 默认”的固定优先级解析，未配置时禁止静默回退；
19. GUI 默认环境只作用于新任务，已有任务始终保留创建时固化的环境绑定；
20. 共享环境默认禁止 agent 修改，只有用户显式允许后才可通过 Boom 环境工具安装依赖。

## 16. 实施完成与后续维护

原“下一落地切片”已经完成，并随后完成 M3、M4、M5、输出治理和评估工具。维护时以以下
不变量为准：

1. solver/worker 只使用 `boom-exec`，不恢复内置 `bash`；
2. 环境绑定来自宿主持久状态，主 agent、intake、worker 和检查点看到一致摘要；
3. Python 档案是共享工具链，不是安全沙箱；未知程序只进入 `isolated`；
4. 分支只写自己的目录，宿主只合并有真实证据路径的事实；
5. 自动 trigger 必须通过去重、冷却和剩余预算门槛；
6. 高风险/高成本动作必须先完成 falsification 门控；
7. solver 自述不能升级为确定性验证，模型复核只能记录为 `model-review`；
8. `finish=length` 仍只恢复一次，首次截断落盘且恢复前检查剩余时间与预算；
9. 已知答案、Provider 凭据和宿主完整环境不进入模型工作区或模型命令；
10. `ctf/runs/` 属于用户运行产物，不由实现或测试收尾清理。
